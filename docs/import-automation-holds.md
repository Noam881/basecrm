# Persistent import automation holds

Import holds retain eligibility decisions for exact CRM resources; they do not change task status, authorize a customer write, stop integrity events, or grant Vault access. Historical writers must create the resource and its hold inside the **same outer database transaction**, so after-commit consumers cannot observe a newly imported resource before its hold exists. Existing resources can be held separately before a reviewed historical update.

For an existing resource, **place its hold before calling an owning writer or acquiring the writer's row locks**, inside the outer transaction. Placement and delivery both acquire the subject advisory lock before the owning resource row lock. Calling `Tasks::update()` (or another writer) first and then placing a hold reverses that order and can deadlock with delivery. Acquire multiple resource holds in a consistent module/source/ID order. For a newly created resource, which is invisible outside the outer transaction, place its hold immediately before that transaction commits. Hold rollback must accompany a failed resource write.

`Awove\Core\Imports\AutomationHolds` provides:

- `placeNative(actor, boundary, batchId, 'lead'|'task', recordId)` checks the fresh operator's `imports.manage`, active/verified status, runtime/batch boundary, open batch and current Lead update policy. Task holds additionally enforce the same assignee/assignment rule as Task updates.
- `placeReminder(actor, boundary, batchId, module, source, recordId)` resolves an exact currently enabled `ReminderSource` from the module registry. The source must implement `ImportHoldSource::authorizeImportHold()`, which locks and checks its owning module's existing edit policy. Callers cannot supply model classes, table names or SQL.
- `release(actor, boundary, holdId, reason)` repeats the current operator, batch and owning-resource authorization checks. Reasons are `reviewed_activation`, `cancelled_import` or `incorrect_scope`. Released history is retained; a new reviewed batch is required to place another hold after release.

Native subjects use the reserved `core/lead` and `core/task` namespaces. Other subjects use the exact registered module/key/record ID, including Marketing `content`, Finance `collections`/`expenses`, and shared work/routine source keys. A resource remains held while **any** batch has an active hold. Holds do not expire with time, resource versions, batch pause/resume, module disablement, application-key changes or runtime boundary changes. Write/release boundary mismatches are refused; background lookups conservatively honor every active hold for the exact resource in the current database.

The scheduler excludes held native tasks and parent leads. Both reminder delivery jobs recheck persisted holds under the same transaction-scoped subject advisory locks used by placement/release. This also guards jobs queued before a hold was created. Shared reminder previews and native reminder queries hide held notices without deleting retained notification history. If the hold table is not yet migrated, or runtime validation fails, reminder automation fails closed without querying a missing hold table; hold writes are refused until migration. Security notifications remain available.

Deploy the schema and restart all queue workers onto the guarded code before starting a historical import. New workers safely suppress reminder delivery while the table is unavailable; the periodic scheduler can enqueue still-due work after rollout. Old workers do not know about holds, so mixed worker versions are not an approved import runtime. Eligibility/boundary checks are fresh; there is no process-wide positive cache.

`Access::canReceive()` and domain integrity events remain unchanged. In particular, `LeadCreated` still creates required extension rows, and Vault role/user/logout revocation listeners and sign-in/factor emails still run. Sales communication records and Marketing records/history are not outbound senders and remain writable under their normal policies.

There is currently no implemented customer WhatsApp/email/calendar transport to gate. Any future automated outbound handler must associate its work with the originating held resource, check the persisted hold before enqueueing and again at delivery, and preserve ordinary authorization checks. A process-local historical flag or event origin alone is insufficient. No importer, provenance store, file journal, recovery procedure or full-migration completion claim is added by this capability.
