# Ordinary legacy lead history

`Awove\Core\Imports\LegacyHistory` preserves ordinary source updates, replies and original source-creator attribution in the existing append-only `crm_activity` table. It does not fetch source data, write files, import customer fields or enable integrations. It is not a Vault or Finance history store. Provider adapters remain responsible for approved source scope and exact relationship evidence; no new user accounts or invitations are created.

## Writer contract

`append(actor, boundary, batchId, parentMappingId, input, payload)` has no HTTP write endpoint. Every write requires a fresh active, email-verified actor with `imports.manage`, the current installation/runtime boundary, an open retained batch, and the actual current Lead update policy before and after the write. The parent must be a verified source **item** mapping to an existing `core.lead`, with a retained verified receipt in the same provider/account/boundary. The independently supplied source parent ID must equal that mapping's source item ID. There is no arbitrary destination Lead ID or caller-supplied fingerprint.

Input keys are exact: `kind` (`update`, `reply`, `source-created`), opaque `source_id`, opaque `source_parent_id`, integer `revision` (1–1,000,000), UUID `request_key`, nullable `previous_receipt_id` and nullable `reply_to_mapping_id`. A source-created snapshot uses its actual parent item ID as `source_id`. Replies require an exact retained update mapping from that same source item; later body revisions cannot move a reply to another update. Global source-ID uniqueness and complete source coverage remain the provider adapter's responsibility.

Payload keys are exact: `body_html`, `author` (`source_id`, `name`), `source_created_at`, `source_updated_at`. Source IDs/names and timestamps may be unknown (`null`). Updates/replies require an available HTML string, including an observed empty string; a source-created snapshot has no body (`null`). Missing/inaccessible bodies are not converted to empty history. Timestamps retain their exact reported RFC3339 strings, including offsets and up to nine fractional digits, without inventing a time or converting a date-only value into midnight.

The host and reusable Core package declare the PHP DOM extension as a runtime dependency. Original HTML is retained unchanged server-side. Derived display text preserves paragraph, line and table-cell boundaries; script/style/active embedded content never executes. Eligible bounded HTTP/HTTPS/mailto/tel destinations are included as plain text without fetching, redirecting or producing active links. Unsafe schemes, userinfo and control-bearing destinations are excluded from display. Embedded media presence is retained as provenance; source media URLs are not returned. The UI points to Documents for available files. This presence flag does not describe import progress or prove attachment inventory or migration completion.

The HTML and derived text limits are each **1 MiB**. Author names are at most 255 characters/1,024 bytes; link destinations are bounded at 2,048 bytes. Document/entity declarations, invalid UTF-8/NUL values and unsupported parser depth/resources are refused. Parsing is bounded to depth 128 and 100,000 visited nodes. Unsupported/oversized data must remain explicitly unresolved in the coordinator; no stored body is silently truncated or discarded.

## Immutable revisions and atomicity

A canonical family derives from the retained parent source identity, kind and opaque source ID. Each explicit source revision has its own deterministic occurrence key and permanently accepted `core.activity` target. These source revision numbers are distinct from the metadata ledger's revision: each immutable occurrence starts at ledger revision 1. Revision 2 requires the verified previous source revision receipt; it appends a new Activity without replacing revision 1. Mapping/code/plan context changes, target changes, gaps, unresolved previous mappings or changed content submitted under an existing occurrence require review.

The writer computes keyed source and actual destination fingerprints itself. A transaction-scoped family advisory lock serializes revision checks. Claim, Activity and verified receipt commit in one SQL transaction. The Activity/finish use a savepoint: if finish expires/refuses, both are rolled back and only the ledger reservation/reconciliation status is retained. Previously claimed requests are status-only; they are never silently taken over. Same-request verified replay rechecks actual Activity bytes and reads back the original finish; new requests observe the actual retained target. No fabricated observed digest, new reconciliation mode or ledger authorization is introduced.

Lock order is batch, canonical family advisory lock, parent mapping, Lead, then occurrence ledger mapping/operation. Call this writer before taking existing owning-row locks in an enclosing import transaction; do not wrap independently ordered multi-family writes around it. Newly created unpublished parents have no competing readers. There is no source/network/file I/O inside its SQL transaction, and native integrity/security events remain enabled.

The native Activity actor is null for legacy attribution; native `created_at` is the actual ingest time. Original author/time are separate source fields. The actual ingester/time comes from the verified operation receipt. Unknown original attribution is labelled unavailable rather than assigned to “System” or the importer. Existing normal activity records and their UI remain unchanged. Archived target Leads fail the existing update policy: import history before applying a reviewed archive state; an already archived target needs a separately reviewed policy, never an automatic unarchive.

## Read contract

`GET /leads/{lead}/legacy-history?before={activityId}` returns up to ten entries, each with an 8 KiB UTF-8-safe text preview, an explicit `has_more_text` flag and a cursor. `GET /leads/{lead}/legacy-history/{activityId}` returns that authorized entry's complete plain text. Both require a fresh active, verified viewer with current Lead view access and scope every entry to that Lead; `imports.manage` is unnecessary for ordinary reading. Responses are private/no-store and nosniff.

Original HTML and internal source/receipt metadata are never serialized into these DTOs or initial Lead props. Legacy Activity serialization also hides its raw details as a defense against accidental model responses. Preview shortening is explicit and reversible through the full-text read; it does not change stored content.

Pages use descending Activity IDs (ingest order). The eventual adapter must append initial source history oldest-first by available original creation time while respecting parent-before-reply dependencies. Unknown times stay unknown; deterministic source order does not invent timestamps. Source edits append later revisions. This capability alone does not establish source completeness, protected staging, file recovery, financial imports or Vault migration.
