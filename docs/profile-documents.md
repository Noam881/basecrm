# Profile documents

Documents is a shared Core capability on the existing contact and company profiles. It adds no navigation entry or business module. General client attachments belong here; proposal versions, signed contracts and encrypted Vault attachments retain their existing dedicated services.

The additive `crm_documents` table references exactly one existing contact or company. Every list, upload and download checks that profile's current permissions. Uploads require edit access; readable profiles allow private attachment downloads. Reassignment and account deactivation affect subsequent requests. The service rechecks the actor and parent under the existing identity lock before storing an upload.

Uploads preserve the original UTF-8 basename and detected MIME type, use a random installation-local private path and verify stored bytes against a SHA-256 digest before committing metadata. Paths and digests remain server-side. Supported formats are PDF, Word, Excel, CSV, text, JPEG, PNG, GIF, WebP, ZIP and MP4, up to 100 MB. Downloads use attachment disposition, no-store and nosniff headers. Videos are private downloads, with no inline player or public URL. This validation does not constitute a malware scan.

Records and files are retained as client history. Corrections are new uploads; this capability has no replace or delete action. The additive migration does not change existing identities or lead records, and its rollback refuses destructive table removal. Recovery uses a tested, consistent database and private-storage backup.

`uploaded_by` and `created_at` describe the actual CRM upload. They must not be rewritten to imply that an imported source author performed that action. Source asset IDs, source relationships and original authors/timestamps belong in the reviewed migration provenance ledger; the current capability alone is not a completed historical import.

Production PHP and reverse-proxy request limits must accommodate the chosen file size and multipart overhead. Capacity planning and backups must include the installation's private `documents/` storage alongside its database. Missing files remain visible as unavailable; they must not be silently removed from the document inventory.

The focused backend suite covers profile permissions, revocation, cross-profile/type binding, metadata privacy, original filenames, exact downloaded bytes, file validation, failure cleanup and an additive migration around existing records. Local browser verification uses only guarded fictional accounts and preserves private recovery copies of the exact selected test files. Earlier fixture-recovery formats remain supported.

Generated source documents reuse this private storage and its durable import journal. `DocumentImporter::importGeneratedDocument` accepts a genuine `workdoc` or `item-description` source, its verified actual Item/parent mappings, real document/file IDs and a registered `GeneratedDocumentSourcePolicy`. There is no default source registration or HTTP import endpoint. A source policy must authorize the exact document and content before retention; the same source must be authorized before a provider adapter fetches its body. Generated content cannot enter through the uploaded-file method.

The native writer makes a clearly labeled TXT export of the original document metadata and ordered block graph. Serialized block JSON strings, authors, dates and parent relationships are retained exactly; JSON/HTML is never rendered. A description is not a Workdoc or a fabricated uploaded asset. Source timestamps are derived only from the document's genuine metadata: a date-only value remains a date in the export and leaves a timestamp-only source field null. Item or attachment authors/times never substitute for a missing document author/time. The immutable first snapshot has revision 1; identical replays reuse the verified document, and changed originals conflict rather than creating arbitrary revisions.

The source policy also approves an immutable `access_scope`. Normal `profile` exports require both the current profile and any source Lead access on list, metadata and download. Unknown ordinary internal documents use `import-review`: this requires an active, verified actor with `imports.manage`, a verified source-account `internal-company` identity, and actual internal Item/subitem/parent context. Ordinary Company visibility alone cannot reveal their row, filename, source metadata or bytes. Review documents are labeled “Unclassified source document — review required”, retain their complete originals and unresolved-purpose flag, and create no customer Lead, Activity, Marketing classification, financial fact or Vault record. Later classification is a separate reviewed action and cannot silently rewrite the receipt or broaden the original scope. This adds no module, route, table or staging store.

All document downloads recheck the fresh actor, profile association and imported source authority inside the stream callback immediately before the first byte. A permission, source Lead, parent-board or identity-mapping change after response creation therefore emits no bytes and closes the already opened handle. The check also applies to ordinary uploaded files without altering their stored metadata or serialization.

Document graphs are bounded to 1,000 blocks and 2 MiB of structured originals, with a 3 MiB generated-export limit. Duplicate, orphaned, cyclic or foreign-document blocks fail before reserving a file. Source mappings, content ownership, permissions and committed byte readback are checked through the existing importer; failed commits retain the owned durable journal for explicit reconciliation. Credential sources remain excluded by the owning source policy and must use the Vault path.
