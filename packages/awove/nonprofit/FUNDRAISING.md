# Fundraising capability

`nonprofit:fundraising` is independently enabled within the optional `awove/nonprofit` package (1.0.0, Core ^1.1/contract 1). The Hebrew source alias עמותה belongs to the Nonprofit module metadata; English remains the interface language. Programs, Projects, Sales, HR, Operations, Assets and Finance are unnecessary for donor contexts, manual next actions and pledges. Enablement grants no staff permissions.

## Shared identities and private context

Core Contact/Company IDs remain canonical. Existing Donor, Partner and Prospect classifications are selected through `IdentityRelationships`; contextual classification uses the same directory and its separate manage/assign/underlying-identity permissions. Nothing automatically merges matching names, creates a copied donor address book or adds a Customer classification for Finance.

A Fundraising context adds its own engagement owner, notes and paired next action/date to one shared classification. Its engagement owner is separate from the shared classification's generic responsible person, as with other domain records. That ownership never grants access to the underlying identity. Context, pledge and receipt access requires both current Fundraising own/all scope and current Core classification/identity scope. Hidden relationships are not exposed through tables, selectors, exports, reminders or direct requests. Inactive historical classifications remain references; new contexts choose an active classification. Contexts are unique per retained classification, including archived contexts.

`nonprofit.fundraising.view.own/view.all`, `create`, `edit.own/edit.all`, `assign`, `archive` and `export` are explicit. Monetary pledge view/manage and actual receipt view/manage are separately granted as `nonprofit.fundraising.pledges.view/manage` and `.receipts.view/manage`. Manage also requires view and editable parent scope. Assigning an owner requires the assign grant and an active person who already has this capability and current access to the selected shared classification/identity. Existing inactive/null owners survive unrelated edits.

## Pledges and actual receipts

A pledge records an optional reference, exact positive amount, original currency, expected donation date and optional donation restrictions. Blank restrictions mean unrestricted. Expected pledges and actual receipts are separate measures. No automatic paid/fulfilled pledge lifecycle is invented. The expected-date view means that date has arrived, not that an unpaid balance was proven. Follow-up completion/rescheduling is explicitly clearing/changing the context's paired next action/date.

Amounts use Core Money, never binary floating point. Core Currency registers `nonprofit_pledges` even when the capability is disabled. Retained-currency mismatch blocks new monetary writes and complete monetary overview totals; values are never converted or relabelled. Pledge and context archive retain records, snapshots, receipt links and history. Pledge edits retain the original currency; archive is nonmonetary and does not require rewriting a mismatched snapshot.

Finance is an optional read-only counterpart. With Finance Collections and current Finance plus Fundraising receipt permissions, a pledge may explicitly link an existing received `finance_payments` row for the same persisted Core identity. Finance's Customer classification must already exist; Fundraising creates no charge, customer role, invoice, donation receipt, payment or external action. `Ledger.total` is an expected charge and is never counted as actual receipt. The Finance Payment's amount, paid date and parent's original currency define the actual receipt.

Linking locks the Fundraising parent/pledge and Finance parent, checks their current versions and scopes, and rejects duplicate active Payment links across Fundraising pledges. One link represents one complete existing Payment; allocation, refunds, credits and overpayments are not invented. Explicit unlink archives the relation and retains its actor/history; it does not delete or alter Finance. A corrected link can then be recorded. Receipt references have no unconditional foreign key to optional Finance tables, so a standalone installation does not require that package's schema.

The optional adapter checks installed code, capability availability, fresh user, current Fundraising parent and Finance parent, current customer/donor identities and the immutable Payment. Its public reference method reloads arbitrary passed context models rather than trusting cached ownership or relationship attributes. If Finance is absent, disabled or inaccessible, actuals are unavailable rather than zero. If any retained active receipt becomes inaccessible or mismatches the pledge's retained currency, the complete total is withheld; authorized individual receipts retain their original currencies. Hidden link IDs/values survive unrelated saves without being returned. Losing the separate receipt-view grant removes actuals and selector props entirely.

## Dates, reminders, tables and reports

The sole reminder source is `nonprofit/fundraising-actions`. A context's next action and date must both be entered or both cleared. Notices store IDs/versions only. The current active recipient, capability, parent/identity scope, ownership, version, archive and due date are checked for enqueue/list/read/delivery. Rescheduling, clearing, archive, access loss or disabling Fundraising suppresses obsolete work. Reading a notice does not finish the action. Dates use the installation timezone; no recurrence or automatic communication is generated.

`/nonprofit/fundraising` provides contexts and a separately permissioned Pledges table, scoped classification/owner/period/date-due/archive views, shared advanced columns/search/sorts/filters/layouts and matching CSV. Stable table IDs are `nonprofit.fundraising-constituents` and `nonprofit.fundraising-pledges`. Context periods use next-action date and pledge table periods use expected donation date. Overview pledged amounts use expected dates; actual receipt totals independently use Payment paid dates for the same authorized engagement owner/classification filters, including retained archived contexts/pledges with active receipt links. Active expected pledges/counts remain separate; archiving an expectation cannot erase linked actual receipt history. Distinct active Payment IDs prevent double-counting; incomplete counterpart coverage withholds a complete actual total. The UI labels these different date bases explicitly.

CSV is the supported spreadsheet export, capped at 5,000 filtered rows with shared formula escaping. It includes only current authorized business columns and never exports Finance IDs/receipt values as a substitute for the distinct financial report. No Excel workbook/import capability is claimed. Every meaningful child mutation increments the context version; stale context/pledge/link/Finance versions reject with HTTP 409. Basic append-only audit stores actor/time/event/changed field names without copying sensitive old/new financial values.

## Implementation and verification

Owned PHP lives in `src/Fundraising`; the aggregate module delegates to `Capability` and loads `routes/fundraising.php`. Migration `2026_10_31_001310_create_nonprofit_fundraising.php` adds four owned tables through controlled install/update commands only. Destructive down migration is unsupported: restore a tested backup.

`NonprofitFundraisingTest` exercises independent operation, own/all/Core identity scope, private monetary fields, optimistic versions, actual-versus-expected receipt dates, duplicate/replayed/wrong-donor links, no Finance writes, optional access loss, exact currency, scoped CSV and stale reminders. Finance-dependent acceptance cases explicitly enable Collections; the standalone persisted-context/pledge case enables only Fundraising. Guarded browser fixtures use reserved `nonprofit-fundraising-{desktop,mobile}@alpha.example.test` accounts, exact fictional contacts, actor/FK checks and private snapshots before narrow cleanup. Browser proof creates a donor context and pledge, links an independently seeded actual Finance Payment, edits/reloads, reschedules a follow-up and downloads filtered CSV on both viewport sizes. Actual run results belong to the maintained verification ledger.

Source-deferred: grant applications, funder reporting, safeguarding casework, participant assessments, donation receipting and external reporting integrations. No promotional messaging, AI drafting, accounting, external integration or automatic Finance write is introduced.
